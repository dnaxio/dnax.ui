Every screen is built from the same outer shell: a **theme root**, some **bars**, an
optional **drawer** and the **page**. Each piece has its own page — this one shows how
they are wired together and which of the two available shells to pick.

| Piece | Role | Page |
| --- | --- | --- |
| `<q-config-provider>` | theme (colors, `mode`, default props) + the programmatic `$q` providers | [Config Provider](/docs/layouts/config-provider) |
| `<q-layout>` | the 3×3 grid that places the zones | [Layout](/docs/layouts/qlayout) |
| `<q-header>` | top bar | [Header](/docs/layouts/header) |
| `<q-back-header>` | back bar, stacked above the header | [Back Header](/docs/components/back-header) |
| `<q-sidebar>` | left or right drawer | [Sidebar](/docs/layouts/sidebar) |
| `<q-page>` | the content zone, usually wrapped in a `<q-container>` | [Page](/docs/layouts/page) |
| `<q-footer>` | bottom bar | [Footer](/docs/layouts/footer) |

## Minimal shell

The shortest version that already behaves — a theme root, the grid, the page. The
middle row of `view` has no `l` / `r`: there is no drawer.

```vue
<template>
  <q-config-provider>
    <q-layout view="hHh .p. fFf">
      <q-header>…</q-header>
      <q-page>…</q-page>
      <q-footer>…</q-footer>
    </q-layout>
  </q-config-provider>
</template>
```

## Full shell

Everything in one screen: a header, a drawer, the page and a footer. The letters are
the ones of the default `view` (`hHh LpR fFf`), so no bar needs a prop — **the case of
its letter in `view` is enough** for it to keep its place while the page scrolls. The
page sits in a `<q-page-container>` (the Quasar structure) — [Page Layout](/docs/layouts/page)
explains when it is worth it.

#code

```vue
<template>
  <q-config-provider :theme="{ mode: 'system' }">
    <q-layout view="hHh LpR fFf">
      <q-header bordered>
        <q-toolbar>
          <q-icon name="lucide:terminal" size="20px" />
          <b>Console</b>
          <q-space />
          <q-btn flat round dense icon="lucide:search" aria-label="Search" />
        </q-toolbar>
      </q-header>

      <q-sidebar side="left" show-if-above bordered>
        <q-sidebar-content>
          <q-sidebar-menu>
            <q-sidebar-menu-item>
              <q-sidebar-menu-button label="Dashboard" icon="lucide:layout-dashboard" active />
            </q-sidebar-menu-item>
            <q-sidebar-menu-item>
              <q-sidebar-menu-button label="Projects" icon="lucide:folder-kanban" badge="3" />
            </q-sidebar-menu-item>
          </q-sidebar-menu>
        </q-sidebar-content>
      </q-sidebar>

      <q-page-container>
        <q-page>
          <q-container>…</q-container>
        </q-page>
      </q-page-container>

      <q-footer bordered>
        <q-toolbar>Dnax UI · console</q-toolbar>
      </q-footer>
    </q-layout>
  </q-config-provider>
</template>
```
::

The frame above is a **containerized** layout (`container` + an explicit height) — that
is what lets it live inside this page. A real app leaves `container` out: the layout
then fills the viewport and the **document** does the scrolling, which is why a
`sticky` bar is enough (no `fixed` position, no offset to compensate).

## Drawer over the content

Drop `show-if-above` and the very same drawer becomes an **offcanvas** panel driven by
`v-model`: it leaves the grid, covers the content from the edge, and closes on Esc, on
the backdrop, with a swipe — or with the browser's back gesture. That is the mobile
behaviour of the component, and the `☰` button does nothing visible on wide screens
where the drawer is already part of the layout — see
[Sidebar](/docs/layouts/sidebar) for `breakpoint`.

::prose-show-case
:dnax-demo-app-layout{demo="drawer"}

#code

```vue
<script setup lang="ts">
import { ref } from "vue"

const open = ref(false)
</script>

<template>
  <q-layout view="hHh .p. fFf">
    <q-header bordered>
      <q-toolbar>
        <q-btn flat round dense icon="lucide:menu" aria-label="Open sidebar" @click="open = true" />
        <b>Console</b>
      </q-toolbar>
    </q-header>

    <!-- Sans show-if-above : le tiroir est en mode offcanvas (piloté par v-model) -->
    <q-sidebar v-model="open" side="left" bordered>…</q-sidebar>

    <q-page>…</q-page>
  </q-layout>
</template>
```
::

## Fixed bars instead of the grid

The other shell: a `<q-app>` whose bars carry the `fixed` prop. Nothing is placed by a
`view` string — the bars leave the flow, and `<q-page>` receives a `padding-top` equal
to the height of the fixed bars before it (and a `padding-bottom` for the ones after
it), so the content is never hidden. Two fixed bars stack automatically: a
`<q-back-header fixed>` first, a `<q-header fixed>` next, and the header settles under
the back bar.

```vue
<template>
  <q-config-provider>
    <q-app>
      <q-back-header fixed title="Details" />
      <q-header fixed translucent>…</q-header>

      <q-page>
        <q-container>…</q-container>
      </q-page>

      <q-footer fixed>…</q-footer>
    </q-app>
  </q-config-provider>
</template>
```

This is the shell used by the [Config Provider](/docs/layouts/config-provider) page, and
the handiest one for a mobile screen: bars stay put, the page scrolls under them.

## Which shell?

| | `<q-layout view="…">` | `<q-app>` + `fixed` bars |
| --- | --- | --- |
| Zones | placed by the 3×3 grid — a drawer on both sides, a drawer above the header… | stacked in the document, in markup order |
| Bars keep their place | the uppercase letter of `view` (`sticky`, clipped to their own cell) | the `fixed` prop (out of the flow) |
| Content offset | the grid cell | `padding-top` / `padding-bottom` published to `<q-page>` |
| Scrolling | the document | the document |
| Good for | a real app shell with a permanent drawer | simple screens, and any embedded layout (`container`) |

## Good to know

- **Direct children only.** The zones are the direct children of `<q-layout>`: the
  matrix is a CSS grid and each zone is a cell.
- **One content child.** Everything that is not a header, a footer or a sidebar lands
  in the page cell — two siblings landing there would overlap, so wrap them in a
  single `<q-page>`.
- **Safe-area insets** are already applied by the bars (top, plus the sides in
  landscape), by the page and by the panels of an overlay. In a mobile app, keep
  `viewport-fit=cover` in the viewport meta: that is what makes
  `env(safe-area-inset-*)` non-zero on iOS. On desktop the insets are `0` and nothing
  moves.
- **Back button.** With the module installed, the browser's back gesture closes the
  open overlay (dialog, sheet, sidebar…) instead of leaving the page.
- **One theme root.** A single `<q-config-provider>` around the shell applies the
  theme to every component and mounts the `$q` providers exactly once.
